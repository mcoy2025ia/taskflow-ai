FASE 0
Decisiones de Arquitectura
Antes de escribir una sola línea de código
⚡Debate — Monolito vs Microservicios
SebastiánLa primera pregunta: ¿monolito Next.js con Supabase o backend separado? He visto equipos perder 3 meses en microservicios para 200 usuarios.
DiegoCon Supabase RLS, el backend "separado" ya existe — las políticas de seguridad se evalúan fila por fila en cada query. No necesitas un API layer intermedio si la lógica de negocio es simple.
ValentinaPero el agente IA sí necesita runtime Node.js completo — streaming SSE, acceso a múltiples APIs externas, loops de tool calling. Edge runtime no sirve aquí. Eso fuerza runtime = 'nodejs' en las rutas de chat.
DiegoExacto. Y eso es un guardrail en sí mismo: el agente solo vive en el servidor. Nunca en el cliente. Las API keys nunca tocan el browser.
ValentinaPara state management: ninguno global. Server Components manejan el 80% del estado. Para interactividad en tiempo real, useOptimistic + useTransition + Supabase Realtime. No hay servidor de estado.
▸ Decisión de Consenso: Arquitectura
Browser → Next.js Server Components / Server Actions → Supabase (RLS)
↓
/api/chat (Node.js) → DeepSeek LLM → Tools → Supabase
/api/embed (service_role · HMAC) → Voyage AI
Regla de oro: nada que sea secreto llega al cliente. Nada que sea mutación llega sin validación Zod.

🛡️Debate — Migraciones & RLS
DiegoAquí es donde la mayoría falla. RLS mal configurado retorna array vacío silenciosamente — nunca error. Tu aplicación funciona "bien" en staging y filtra datos en producción.
Valentinahalfvec(512) usa float16 — la mitad de espacio, misma precisión para voyage-3-lite. Con 100k tareas la diferencia es 200MB de índice.
SebastiánEl orden de las migraciones importa tanto como su contenido. Cada migración debe ser idempotente: CREATE TABLE IF NOT EXISTS, CREATE INDEX IF NOT EXISTS.

1.4 RLS — La Capa Más Crítica

-- Funciones helper SECURITY DEFINER (evitan recursión en RLS)
CREATE OR REPLACE FUNCTION public.is_project_member(p_project_id uuid)
RETURNS boolean LANGUAGE sql SECURITY DEFINER STABLE
AS $$
  SELECT exists (
    SELECT 1 FROM public.project_members
    WHERE project_id = p_project_id
      AND user_id = auth.uid()
  );
$$;

-- Políticas para tasks
CREATE POLICY "tasks: propietario puede leer" ON public.tasks
  FOR SELECT USING (user_id = auth.uid());

CREATE POLICY "tasks: solo propietario puede crear" ON public.tasks
  FOR INSERT WITH CHECK (user_id = auth.uid());

CREATE POLICY "tasks: solo propietario puede eliminar" ON public.tasks
  FOR DELETE USING (user_id = auth.uid());
⚠️
Diego — Guardrail de implementación
Después de crear RLS, verificar con service_role que los datos existen, y con anon_key que NO son accesibles. El flujo: (1) supabase db push, (2) insertar datos de prueba con service_role, (3) consultar con anon_key → debe retornar array vacío, no error, (4) consultar con JWT del usuario correcto → debe retornar los datos.
1.5 Embeddings con halfvec

CREATE TABLE IF NOT EXISTS public.task_embeddings (
  task_id      uuid PRIMARY KEY REFERENCES public.tasks(id) ON DELETE CASCADE,
  user_id      uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  embedding    halfvec(512) NOT NULL,   -- voyage-3-lite=512 dims, halfvec ahorra 50%

CREATE INDEX IF NOT EXISTS task_embeddings_hnsw_idx
  ON public.task_embeddings
  USING hnsw (embedding halfvec_cosine_ops)
  WITH (m = 16, ef_construction = 64);

2.2 Variables de Entorno con Validación en Boot
Nunca acceder a process.env.ALGO directamente. Si falta una variable, la aplicación no arranca — el error es explícito.
src/lib/env.ts
import { z } from 'zod'

const envSchema = z.object({
  NEXT_PUBLIC_SUPABASE_URL:      z.string().url(),
  NEXT_PUBLIC_SUPABASE_ANON_KEY: z.string().min(1),
  SUPABASE_SERVICE_ROLE_KEY:     z.string().min(1),
  DEEPSEEK_API_KEY:              z.string().min(1).optional(),
  GROQ_API_KEY:                  z.string().min(1).optional(),
  VOYAGE_API_KEY:                z.string().min(1),
  EMBED_INTERNAL_SECRET:         z.string().min(32),  // mínimo 32 chars
  NEXT_PUBLIC_APP_URL:           z.string().url(),
  CHAT_PROVIDER:                 z.enum(['deepseek', 'groq', 'ollama']).default('deepseek'),
  // Opcionales — sin Upstash el rate limit está desactivado en dev local
  UPSTASH_REDIS_REST_URL:        z.string().url().optional(),
  UPSTASH_REDIS_REST_TOKEN:      z.string().optional(),
})

// safeParse para mensaje de error descriptivo; nunca .parse() que lanza excepción cruda
function validateEnv() {
  const result = envSchema.safeParse(process.env)
  if (!result.success) {
    const missing = result.error.issues.map(i => `  - ${i.path.join('.')}: ${i.message}`)
    throw new Error(`Variables de entorno inválidas:\n${missing.join('\n')}`)
  }
  return result.data
}
export const env = validateEnv()
🔑
Diego — Generación del secret
EMBED_INTERNAL_SECRET mínimo 32 caracteres. Generar con: openssl rand -hex 32. Nunca usar strings predecibles como "my-secret".
2.3 Middleware de Autenticación
middleware.ts (raíz del proyecto)
export default async function middleware(request: NextRequest) {
  // CRÍTICO: iniciar con NextResponse.next({ request })
  // Sin { request }, los headers no se propagan al Server Component
  let supabaseResponse = NextResponse.next({ request })

  const supabase = createServerClient('...', '...', {
    cookies: {
      setAll(cookiesToSet) {
        cookiesToSet.forEach(({ name, value, options }) => {
          request.cookies.set(name, value)
          // CRÍTICO: setear en ambos — request Y response
          supabaseResponse.cookies.set(name, value, options)
        })
      }
    }
  })

  // getUser() valida JWT contra Supabase — NO usar getSession() (no valida)
  const { data: { user } } = await supabase.auth.getUser()

  if (!user && !isPublicRoute) {
    return NextResponse.redirect(new URL('/login', request.url))
  }

  // CRÍTICO: devolver supabaseResponse, NUNCA NextResponse.next() aquí
  return supabaseResponse
}
⚠️
Diego — Trampa frecuente
getSession() usa el JWT del cookie sin validarlo contra el servidor — un token expirado o manipulado pasa. getUser() hace una llamada extra a Supabase pero es la única forma correcta de verificar autenticación en middleware.

Sistema de Tipos y Validaciones
Zod v4 · TypeScript estricto · react-hook-form patterns
🧩Debate — Zod v4 gotchas
SebastiánZod v4 cambió .errors a .issues. Si usas .errors[0].message en tus Server Actions, obtienes undefined silenciosamente — el error se pierde.
ValentinaCon react-hook-form, schemas con .default() tienen una trampa: z.infer<Schema> es el tipo OUTPUT. El formulario necesita el tipo INPUT. Si usas useForm<CreateTaskSchema> con defaults, explota.
DiegoUn schema por entidad. Deriva los tipos del schema, no al revés. Si tienes dos schemas distintos para la misma entidad, eventualmente se dessincronizan.

FASE 4
Server Actions — CRUD Seguro
Auth → Zod → Autorización → Mutación (el orden importa)
▸ Orden de validación no negociable
Cada Server Action es un endpoint de API implícito. Cualquier usuario autenticado puede llamarla directamente, no solo tu formulario. El orden es: (1) Autenticación, (2) Validación Zod, (3) Autorización, (4) Mutación.
src/actions/task.actions.ts
'use server'

export async function createTask(rawData: unknown): Promise<ActionResult<TaskWithAssignees>> {
  // 1. Autenticación
  const user = await getAuthUser()
  if (!user) return { success: false, error: 'No autenticado' }

  // 2. Validación Zod — .issues[0] en Zod v4 (no .errors)
  const parsed = CreateTaskSchema.safeParse(rawData)
  if (!parsed.success) {
    return { success: false, error: parsed.error.issues[0]?.message ?? 'Datos inválidos' }
  }

  // 3. Autorización: si project_id, verificar que el usuario es editor
  if (project_id) {
    const { data: isMember } = await supabase.rpc('is_project_editor', { p_project_id: project_id })
    if (!isMember) return { success: false, error: 'Sin permisos en este proyecto' }
  }

  // 4. Mutación (RLS también protege aquí)
  const { data, error } = await supabase
    .from('tasks')
    .insert({ user_id: user.id, /* SIEMPRE user_id explícito */ ...parsed.data })
    .select()
    .single()

  // 5. Trigger embedding asíncrono (fire-and-forget — no bloquear al usuario)
  void triggerEmbedding(data.id, user.id, title, description)

  revalidatePath('/board')
  return { success: true, data: { ...data, assignees: [] } as TaskWithAssignees }
}
⚠️
Sebastián — redirect() gotcha
redirect() de Next.js lanza una excepción internamente. Si lo pones dentro de un try/catch, el catch lo captura y el redirect nunca ocurre. Siempre llamar redirect() fuera del try.
FASE 5
Pipeline RAG — Búsqueda Semántica
Voyage AI · HNSW · Reranking · Búsqueda Híbrida
🧠Debate — RAG híbrido vs puro vectorial
ValentinaEl error más común en RAG es creer que solo necesitas embeddings. Con tareas estructuradas (status, priority), la búsqueda SQL supera a la semántica para consultas como "¿qué tengo pendiente?". La solución correcta es híbrida.
DiegoEl reranking no es opcional en producción. top-K de vector similarity tiene alta recall pero baja precision. rerank-2-lite re-ordena los candidatos según relevancia léxica. El costo se justifica.
SebastiánEl threshold de similarity es tricky. 0.7 es demasiado alto — con tareas cortas, scores de 0.35 son relevantes. Empezar en 0.3 y ajustar con datos reales.
src/lib/ai/voyage.ts
const EMBED_MODEL  = 'voyage-3-lite'   // 512 dims, óptimo para tareas cortas
const RERANK_MODEL = 'rerank-2-lite'

// Distinción importante: input_type 'query' vs 'document'
export async function generateQueryEmbedding(query: string): Promise<number[]> {
  const res = await fetch(`${VOYAGE_API}/embeddings`, {
    method: 'POST',
    body: JSON.stringify({
      model: EMBED_MODEL,
      input: [query],
      input_type: 'query',   // ← diferente al indexar documentos
    }),
  })
  const data = await res.json()
  return data.data[0].embedding
}
FASE 6
El Agente IA — La Pieza Más Compleja
Tool Calling · Guardrails · confirm_required · System Prompts
🤖Debate — Diseño del agente
ValentinaEl agente tiene dos decisiones fundamentales: cuántos turnos de tool calling permitir, y cómo manejar operaciones destructivas. Para un Kanban, dos turnos son suficientes. Más turnos = más latencia, más costo, más superficie de ataque.
DiegoLas operaciones destructivas son el punto crítico. delete_task ejecutado por un LLM que malinterpretó "elimina los pendientes" podría borrar decenas de tareas. La solución: confirm_required — el agente detecta la tool destructiva, emite evento al cliente, pausa, espera confirmación.
SebastiánEl agente DEBE ser runtime = 'nodejs'. Si usas Edge Runtime para el chat, te enteras de los límites en producción, no en development.
ValentinaEl sistema de herramientas debe ser mínimo. Cada tool que añades es superficie de prompt injection. Seis tools cubre el 95% de casos: crear, actualizar, mover, eliminar, listar, buscar.
src/lib/ai/agent.ts — Loop con guardrails
const DESTRUCTIVE_TOOLS = new Set(['delete_task'])

if (first.finish_reason === 'tool_calls') {
  // ── Guardrail: interceptar destructivas ANTES de ejecutar ──────
  const destructiveCall = first.tool_calls?.find(
    tc => DESTRUCTIVE_TOOLS.has(tc.function.name)
  )

  if (destructiveCall) {
    emit(controller, {
      type:       'confirm_required',   // evento especial al cliente
      tool:       destructiveCall.function.name,
      args,
      task_title: data?.title ?? null,
      confirm_id: crypto.randomUUID(),
    })
    return   // Parar aquí. El cliente maneja la confirmación.
  }

  // Ejecutar tools no destructivas en paralelo
  const toolResults = await Promise.all(
    first.tool_calls.map(async (tc) => {
      const result = await executeTool(tc.function.name, args, { supabase, userId })
      return { role: 'tool' as const, tool_call_id: tc.id, content: result }
    })
  )
}
▸ System Prompt con guardrails explícitos
Cuatro reglas para el LLM: (1) No inventar tareas que no estén en el contexto, (2) No salir del dominio de tareas, (3) Pedir confirmación en ambigüedad destructiva, (4) No ejecutar acciones masivas sin confirmación ("elimina todo", "mueve todas"). Estas reglas combinadas con el guardrail técnico crean defensa en capas.
FASE 7
Multi-tenancy Seguro
Projects · Invitaciones HMAC · RLS multi-owner
🏢Debate — Tokens de invitación
DiegoMulti-tenancy es donde más errores de seguridad ocurren. El patrón incorrecto: "verifico en el frontend que el usuario es del proyecto". El correcto: RLS + is_project_member() que se evalúa en el servidor para CADA query.
SebastiánLos tokens de invitación necesitan entropía suficiente. crypto.randomBytes(32).toString('hex') da 256 bits — imposible de bruteforcear. Expiración de 7 días. Un único uso.
ValentinaEl link de invitación va a /invite/[token] en TU dominio, no a un link externo. El servidor verifica el token, muestra detalles del proyecto, y solo entonces ejecuta accept_invitation.
006_invitations.sql — Función accept_invitation
CREATE OR REPLACE FUNCTION public.accept_invitation(p_token text)
RETURNS jsonb LANGUAGE plpgsql SECURITY DEFINER AS $$
DECLARE
  v_inv public.project_invitations;
BEGIN
  SELECT * INTO v_inv
  FROM public.project_invitations
  WHERE token = p_token
    AND accepted = false
    AND expires_at > now();

  IF NOT FOUND THEN
    RETURN jsonb_build_object('error', 'Invitación inválida o expirada');
  END IF;

  INSERT INTO public.project_members (project_id, user_id, role)
  VALUES (v_inv.project_id, auth.uid(), v_inv.role)
  ON CONFLICT (project_id, user_id) DO UPDATE SET role = excluded.role;

  UPDATE public.project_invitations SET accepted = true WHERE id = v_inv.id;
  RETURN jsonb_build_object('project_id', v_inv.project_id);
END;
$$;

Analítica — Métricas Puras
Burndown · Velocidad · HTML Export sin canvas
▸ Por qué HTML Export, no PDF
Tailwind v4 usa oklch() para colores — oklch no está soportado en html2canvas ni en los motores PDF vectoriales. Resultado: cualquier export basado en canvas produce rectángulos negros donde deberían ir los gráficos. La solución: gráficos con divs Tailwind en pantalla + buildAnalyticsHTML que genera un .html self-contained con estilos inlineados — se abre en cualquier browser, imprime correctamente y no tiene dependencias externas.
src/lib/analytics/metrics.ts — Funciones puras
// Días con fechas UTC absolutas (evita bugs de timezone)
const startMs   = Date.UTC(startDate.getFullYear(), startDate.getMonth(), startDate.getDate())
const endMs     = Date.UTC(endDate.getFullYear(),   endDate.getMonth(),   endDate.getDate())
const nowMs     = Date.UTC(now.getFullYear(),        now.getMonth(),       now.getDate())

const daysElapsed = Math.max(0, Math.round((nowMs - startMs) / 86_400_000))
const daysLeft    = Math.max(0, Math.round((endMs - nowMs)   / 86_400_000))

const velocityActual   = daysElapsed > 0 ? +(done / daysElapsed).toFixed(2) : 0
const velocityRequired = daysLeft    > 0 ? +(pending / daysLeft).toFixed(2) : 0
const atRisk           = velocityRequired > velocityActual && daysLeft < 14

Vitest · Mocks Supabase · Cobertura 70%+

FASE 17
Operación en Producción — Incidentes Reales
Rescate de infraestructura · Migración de LLM · Fail-open · Modo invitado · Julio 2026
▸ Por qué existe esta fase
Construir es la mitad del trabajo. Esta fase documenta lo que pasó después del primer deploy: dependencias externas que murieron sin aviso, tiers gratuitos que se pausan solos, y el primer usuario invitado que borró el tablero demo completo. Cada incidente dejó un patrón de defensa reutilizable.
INCIDENTE 1 Proyecto Supabase perdido — restauración desde cero
🗄️
uuid_generate_v4() no existe en proyectos Supabase nuevos · RESUELTO
Al aplicar las migraciones en el proyecto restaurado, 003_embeddings.sql falló con 42883: function uuid_generate_v4() does not exist — la extensión uuid-ossp no se instala igual en todos los proyectos. Corrección: reemplazo global por gen_random_uuid() (nativa de PostgreSQL 13+, sin extensión). Regla: nunca dependas de uuid-ossp en migraciones nuevas.
🌱
Re-seed completo: 60 tareas Olist · 5 roles · 60 embeddings
Proyecto "Olist E-commerce Analytics & ML" (Sodimac · Mercadeo) con 6 fases (Análisis → Bronze → Silver → Gold → ML → Reportes), equipo de 5 roles (Data Engineer, ML Engineer, Data Analyst, Business Analyst, Scrum Master) y embeddings Voyage regenerados respetando el límite de 3 RPM del tier gratuito (21s entre requests — no los 100/min del tier pago). La migración 013_project_company_fields.sql agregó company y department a projects.
🔒
El trigger de user_id inmutable se respeta — no se salta
Al reasignar las tareas por rol, el trigger trg_tasks_immutable_user_id (FASE 16, BLOCKER #3) bloqueó los UPDATE de user_id — incluso con service_role. Decisión correcta: no saltarlo. tasks.user_id = creador inmutable; task_assignments = asignación mutable y fuente de verdad para avatares y filtros del Kanban. La protección de seguridad forzó el diseño correcto.
INCIDENTE 2 Upstash eliminado — el rate limiter tumbó el chat completo
🔴
DNS ENOTFOUND en Redis → 500 en /api/chat, /api/report y /api/audit · CORREGIDO (ratelimit.ts)
La instancia de Upstash fue eliminada (dominio inexistente). ratelimit.ts verificaba que las env vars existieran, pero no capturaba el fallo de red de .limit() — la excepción tumbaba las 3 rutas con 500. El síntoma visible era engañoso: "Sin análisis narrativo disponible" en el informe PDF, que parecía un bug del LLM. Corrección: fail-open con try/catch — si Redis no responde, la request pasa sin límite y se loguea el warning. Lección: el rate limiting es protección de costos/abuso, no un control de seguridad — jamás debe ser single point of failure del producto.
INCIDENTE 3 "This page couldn't load" — el middleware sin timeout
⏱️
Supabase free-tier se pausa por inactividad → getUser() cuelga toda navegación · MITIGADO (middleware.ts)
middleware.ts llama supabase.auth.getUser() en cada navegación. Cuando Supabase (plan gratuito) se pausa y tarda en despertar, esa llamada se cuelga indefinidamente — el navegador muestra el error genérico de conexión. Corrección: Promise.race con timeout de 5s que trata el timeout como no-autenticado y redirige a /login. No evita la pausa de Supabase, pero convierte "pestaña muerta" en "recarga y funciona".

▸ Por qué fue barato migrar — y cómo se verificó
La API de DeepSeek es OpenAI-compatible: mismo formato de tool_calls, mismo SSE data: {...}. El parser del agente no cambió ni una línea. Antes de desplegar se verificó por capas contra la API real: (1) completion básica, (2) tool calling con una tool del agente, (3) streaming. INCIDENTE 4 El primer invitado borró el tablero demo
👤

El login de invitado (DEMO_EMAIL) compartía permisos con cualquier usuario — incluido deleteAllTasks. Un solo visitante podía vaciar el demo para todos los siguientes. Corrección en dos capas obligatorias: (1) UI — el botón redirige a /register en vez de abrir el diálogo destructivo (board-actions.tsx); (2) Server Action — deleteAllTasks rechaza explícitamente si user.email === env.DEMO_EMAIL, porque la UI se puede saltar invocando la action directo. Regla nueva de seguridad: toda acción destructiva futura replica ambas capas.
UX + IA "Generar con IA" — el usuario revisa el prompt antes de gastar tokens
▸ De botón opaco a modal transparente
El botón generaba 90 tareas con un prompt hardcodeado invisible. Ahora abre un modal que pide empresa, proyecto/área y participantes (chips con los miembros reales del proyecto, prefill desde projects.company/department), muestra las instrucciones completas en un textarea editable con botón de restaurar, y un <details> con el prompt final exacto que se enviará. Detalle de arquitectura: el prompt default vive en src/lib/ai/generate-tasks-prompt.ts — un módulo 'use server' solo puede exportar funciones async, no constantes, así que compartir el texto entre server y client exige un módulo aparte. generateTasksCSV(customPrompt?) valida con Zod (max 4000) antes de llamar al LLM.
▸ Patrones que deja esta fase
Fail-open en dependencias no críticas — si un servicio auxiliar (rate limit, telemetría) muere, el producto sigue; solo las dependencias de seguridad fallan cerrado.

Timeout en todo I/O del hot path — cualquier fetch en middleware o layout necesita Promise.race; sin timeout, la latencia de un tercero se convierte en tu downtime.

Doble capa para acciones destructivas — UI que guía + Server Action que rechaza. La UI es UX, el servidor es la seguridad.

Abstracción OpenAI-compatible — cambiar de proveedor LLM costó ~1 hora porque el agente habla el dialecto común, no el SDK de un vendor.

Capas de seguridad
🛡️
Row Level Security
Activo en todas las tablas de Supabase. Cada query se valida fila por fila con el JWT del usuario — no hay forma de acceder a datos ajenos aunque el código tenga un bug.
⏱️
Rate Limiting asimétrico
Máximo 20 requests/min por user.id en el endpoint de chat (Upstash sliding window). Bot Guard detecta patrones sospechosos antes de llegar al LLM.
🔐
Auth · getUser() sobre getSession()
Cada Server Action y API route verifica identidad llamando getUser() — nunca getSession(), que puede ser falsificada desde el cliente.
🔗
Invitaciones HMAC
Los enlaces de invitación a proyectos están firmados con HMAC-SHA256. Un token manipulado es detectado y rechazado antes de procesar la solicitud.
🪖
Headers HTTP
Content Security Policy, X-Frame-Options, Permissions-Policy y Referrer-Policy configurados en next.config.js. Sin fuentes externas no declaradas.
⚠️
Guardrail destructivo
Eliminar una tarea nunca se ejecuta directamente. El agente emite confirm_required y espera confirmación explícita por clic — nunca por voz.
Guía de Reutilización

Todo lo que necesitas para clonar este proyecto, conectar tus propias credenciales y tenerlo corriendo en menos de 30 minutos. Sin suposiciones — cada paso es ejecutable.

PASO 3
Crear proyecto Supabase y aplicar migraciones
Base de datos · Auth · RLS · pgvector
3.1 Crear el proyecto en Supabase Dashboard
Ve a supabase.com → New Project.
Anota estos 3 valores que usarás en el paso 4:
Project URL → Settings → API → Project URL
anon key → Settings → API → Project API keys → anon public
service_role key → Settings → API → Project API keys → service_role (secreto, nunca al cliente)
3.2 Habilitar la extensión pgvector
Supabase Dashboard → SQL Editor
create extension if not exists vector;
3.3 Vincular y aplicar las 13 migraciones
Terminal
# Vincular al proyecto (obtén el project-ref en Settings → General)
npx supabase link --project-ref <tu-project-ref>

# Aplicar las 13 migraciones en orden
npx supabase db push
⚠️
Verificar que se aplicaron las 13 migraciones
En Supabase Dashboard → Table Editor debes ver las tablas: profiles, tasks, task_embeddings, projects, project_phases, project_members, chat_sessions, messages, comments, invitations. Si alguna falta, revisa la salida del db push.

▸ Reindexar embeddings después de cambiar tareas masivamente
Si importas tus propias tareas por CSV o modificas títulos/descripciones en bulk, corre el script de backfill para que el RAG tenga contexto correcto:

El script respeta el rate limit de 21 req/s de Voyage AI. Para 500 tareas tarda ~25 segundos.

Si todo pasa, merge a main lanza deploy automático a producción.
